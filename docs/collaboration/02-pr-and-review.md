# PR 与 Review 规范

本文说明本项目 Pull Request 描述、Review 沟通和高风险改动的基本约定。

## PR 说明规范

PR 描述应包含以下内容：

* 改动内容。
* 改动原因或背景。
* 已完成的验证方式。
* 是否涉及环境变量。
* 是否涉及数据结构、权限或外部服务。
* 如果有界面变化，应附截图或说明影响页面。

示例：

```md
## 改动

- 新增活动状态概览入口
- 调整首页项目介绍文案

## 验证

- pnpm lint
- pnpm build

## 注意事项

- 不涉及环境变量
- 不涉及真实社团数据
- 后续需要补充活动详情页的数据接入
```

纯文档改动示例：

```md
## 改动

- 更新 CONTRIBUTING.md
- 更新 Git 工作流和 PR Review 规范

## 验证

- 文档修改，未运行构建

## 注意事项

- 不涉及运行时代码
```

## 高风险改动

涉及以下内容的 PR 应在说明中明确标注影响范围和验证方式：

* AI 聊天入口、提示词、上下文组装或模型调用逻辑。
* 长期记忆、知识条目、活动记录、任务状态等核心数据结构。
* 权限、登录态、成员身份、角色边界和可见范围。
* 真实社团资料、成员信息、活动复盘、经费或物资记录的导入导出。
* 外部服务配置，例如 AI 服务、数据库、对象存储、部署平台和监控服务。
* 构建配置、依赖升级、路由结构和全局样式。

涉及以下文件或目录时应特别说明：

* `src/app/`
* `src/app/globals.css`
* `next.config.ts`
* `package.json`
* `pnpm-lock.yaml`
* 未来新增的数据模型、迁移文件、服务端接口和 AI 调用封装

如果后续项目引入数据库迁移、生产环境部署或真实社团数据，相关操作必须由维护者确认后执行，不得直接在生产环境试验命令。

## Review 沟通规范

Review 应聚焦改动本身，包括正确性、可维护性、安全性和用户影响。

提出意见时应尽量具体，例如：

* “这里是否需要处理没有活动记录时的空状态？”
* “这个输入框在手机屏幕上可能会换行，需要验证移动端。”
* “这里调整了记忆条目的字段结构，PR 说明中需要补充数据影响。”
* “这段提示词会不会把成员隐私信息发送给外部服务？”

收到 Review 意见后，应通过修改代码、补充说明或解释原因来回应。无法立即处理的问题应在 PR 中记录后续安排。
